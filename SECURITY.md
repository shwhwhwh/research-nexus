# Security and privacy

Do not publish credentials or private research in an issue. To report a vulnerability, use the repository's private vulnerability reporting feature when enabled, or contact the maintainer through their GitHub profile without including secrets in a public thread.

The backend binds to loopback and validates Host, Origin, and CSRF tokens. The desktop renderer is isolated from Node.js. Saved service keys use Windows DPAPI; agent authentication stays with the installed CLI. The published template uses a reviewed built-in archive engine; DIY plans use a bounded operation set, origin/credential scoping, version-bound activation and stable write receipts. These controls do not replace careful API permission scoping, plan review, and backups.

`data/` contains private material and is excluded from Git. Screenshots, logs, model requests, and sample payloads may still contain research data: review them before sharing. The published template does not invoke a model provider; research/model use inside OpenResearch follows its own configuration and terms. DIY plan compilation sends the declared purpose/sample to the selected local CLI. Semantic classification sends selected-project citation context only after provider/project-bound consent; future-project auto-onboarding requires a separate grant bound to the local source address and model provider, which fixed-project grants cannot satisfy. Use keyword rules when no such transfer is desired. Codex compiler/classifier invocations disable shell, connectors, plugins, memories and agent spawning without changing global settings. Use minimal, non-sensitive fixtures. Keep Electron and Python dependencies updated and do not expose the local backend to a network.

Use your own accounts, API keys, and provider permissions. Preview tests simulate HTTP and cannot establish live connectivity. POST receipt tracking reduces repeated writes but cannot provide universal exactly-once delivery to arbitrary services.
